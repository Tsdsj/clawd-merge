# M3 评估：先验证每日挑战，再选择扩展

日期：2026-10-03。代码基线：`6a318eb`（T12 已提交）。本轮只做评估与范围建议，不批准 M3 实现、迁移或发布。原 T13—T16 编号保留，下面的 a/b 仅表示建议拆分，不是已领取的任务队列。

## 结论

**M3 不适合整体开工。建议先完成 M2 发布验收与一轮真实反馈，第一候选是 T16a「低特效与舒适性设置」；随后依据反馈选择 T14a「最近对局／附近排名」或 T13a「本机成就」。离线安装、周榜和残局分别立项。**

这是工程收益与验证成本的判断，不是已有玩家反馈证明的需求优先级。M2 尚未形成线上效果证据，现在再叠加多套回访机制，将难以判断哪项功能带来了变化。

## 必须提前收窄的规则

**T16a：只降低视觉/触觉刺激，不改变玩法。** 粒子数量、震屏、闪光与震动可以调节，但物理子步、掉落序列、碰撞、连击计分和输入判定不能随“低特效”变化。系统减弱动态效果应至少默认关闭震屏与强烈装饰动效；震动作为独立设置，默认值需在原型中说明。已有音效开关保留。CSS 偏好只是检测信号，Canvas 必须在 JavaScript 中主动消费；这一点与 [MDN 的 reduced-motion 说明](https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/At-rules/@media/prefers-reduced-motion)一致。

**T14：本人当前名次已经存在，附近排名不是重新做一个个人名次卡。** 附近数据应由完整榜单的排序位置查询，不能只过滤前 100 名。经典当前同分排名逻辑与每日的 player_id 最终排序不同；实施前必须明确是否沿用并列名次、如何稳定返回附近顺序，不能悄悄改变历史排行契约。最近对局接口仅返回已验证本人可访问的字段，不公开他人私有对局或凭证。匿名/离线历史当前无法从服务端补齐，空态必须说清。

周榜不建议把不同日期的每日原始分数直接累加：题目不同，参与天数也不同，这会引入新的积分与公平性设计。首版经典周榜按当前 scores 的接受时间取每人最高分；同分再取首次达成时间，并明确稳定排序。先用真实查询计划判断新增索引，避免为每个筛选条件都建索引；Cloudflare 官方也建议通过 [查询计划核对索引使用](https://developers.cloudflare.com/d1/best-practices/use-indexes/)。

**T13：本机纪念与账号权益必须分开。** 若首版只做本机成就，应明确跨设备不自动同步，也不把本机自报成就当作服务端权威奖励。解锁用集合合并而非相互覆盖；历史上无法可靠证明的累计次数不回填。每日与经典是否共用成就，需要独立定义；不能破坏已有图鉴/偏好隔离。皮肤只改画法，碰撞体、概率和得分保持不变。

**T16b：离线能力限定为曾成功缓存后的再次进入。** 首次从未访问且没有网络不能承诺可用。缓存采用资源清单和应用版本；账号 API、OAuth 回调、成绩请求都不缓存。升级等到当前局安全保存后再提示用户应用，不能在进行中强行 reload。Service Worker 默认等待旧客户端退出，强制激活可能造成新旧代码共存问题，因此需要显式处理生命周期和跨版本存档；参见 [web.dev 的生命周期说明](https://web.dev/articles/service-worker-lifecycle)。

**T15：先证明宽容的解法，再做数量。** 固定棋盘与固定序列仍受瞄准位置、输入发生时机和物理演进影响。优先试“每步落稳后再投放”的离散关卡交互，接受多条解法，目标采用稳定的合成结果而不是像素级终态；这属于新模式规则，需单独原型确认。保存一条参考解及容差范围，在不同帧率/浏览器上重试；如果只能靠精确帧数或极窄落点解出，就停止扩展关卡，先修正设计。

## 建议推进顺序和放行条件

1. **M2 发布验收收尾**：核对 T08—T12 版本，按既有顺序备份/迁移 0004 → Worker → 前端；真实 OAuth、手机触控/后台、系统分享与保存路径补证据。发布与迁移需要另行授权，本轮不执行。M3 不成为 M2 的发布前置条件。
2. **T16a 独立原型**：在现有帮助/设置空间展示最小开关，不重做主布局。确认后再实现。验收包括刷新持久化、系统偏好变化、经典/每日一致，以及相同随机种子与输入下分数/序列不变。性能比较复用 `test/performance.html` 的同场景，并至少补一台手机实际体验；没有证据时只称“减少特效”，不宣传性能提升。
3. **M2 一个完整观察周期**：建议至少覆盖完整一周的北京时间换日，使用 T12 同口径报告，加少量真实试玩反馈。时间长度是排期建议，不保证统计显著性，也不自动新增埋点或监控。先看日题签发/接受、重复接受账号及明确失败反馈；不能把这些重命名为真实留存/上传成功率。
4. **只选择一个下一切片**：成绩找回与竞争定位问题明显，选 T14a；希望有短期收集目标的反馈明确，选 T13a。未出现相应问题就不因任务编号而继续加功能。
5. **独立决定其余项**：T16b 需明确离线需求与更新验收；T14b 需有周期竞争诉求；T13b 需有多设备同步诉求；T15 需先通过单关玩法与解法验证。

## 当前不建议进入的范围

实时 PvP、聊天、公会、复杂货币、付费商店仍不在规划内。限时、低重力、窄棋盘先保留为实验候选。这些都会增加平衡、分榜、反作弊或内容维护成本，当前证据不足以支持扩展。

本轮推荐决策是：**先准备 M2 发布验收；M3 只把 T16a 作为第一设计候选，其余保持待反馈。** 没有新增业务代码、数据库表、依赖、事件采集或 M3 原型。
