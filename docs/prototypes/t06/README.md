# T06 成绩上传可靠性设计

日期：2026-10-02。状态：用户已确认，本地正式实现已接入；原型保留为设计依据。

原型地址：`http://localhost:5174/docs/prototypes/t06/`。演示正在上传、断网暂存、重试暂停、成功、规则拒绝、身份不匹配、本机暂存失败和本地局。点击“再来一局”可查看旧成绩仍待处理的状态；点击“待处理成绩”可演示补传。所有数据与结果都是示例，没有真实持久化、请求或自动重试。

## 产品行为

- 结算仍以“再来一局”为主操作，成绩状态独立显示；开始新局不覆盖旧局结果，不弹出旧局的结算层。
- 区分“已暂存”和“已上传”。只有收到服务端接受回执才显示成功；响应丢失只能显示未确认，不能猜测失败或成功。
- 自动重试有次数上限，耗尽后保留记录并允许手动重试。断网、超时、5xx 不立即丢弃成绩。
- 原凭证不存在的本地局、明确转成本地的恢复局不进入补传队列，不通过重新登录或申请新 session 补交旧分。
- 存储失败时显示“尚未保存，请勿刷新”；保留当前页内存记录，但不声称刷新后仍可补传。
- 待处理入口区分可重试、等待原身份、已被规则拒绝。拒绝原因可查看；不会把全部 4xx 都当作断网重试。
- 非上传中的条目可以主动移除本机记录，需二次确认；移除后不再由本机补传，不删除本机最高分或服务端已接受的成绩。不能以静默清队列代替错误处理。
- 排名若来自稳定回执，标注“提交时个人最佳排名”；最新排名继续查现有排行榜，避免把旧回执排名说成实时排名。

## 服务端幂等与事务

建议新增 `leaderboard/migrations/0003_score_receipts.sql`，为每个服务端 session 建立唯一回执。至少保存 sessionId、所属玩家、原请求的 score/drops/maxLevel、接受时间与原成功响应。首版跟随成绩历史保留，不因开新局清理已用 session 而删除回执。

`POST /api/score` 沿用现有请求字段，身份仍来自 Bearer token；客户端 roundId 用于本地记录关联，服务端以自己签发的 sessionId 作为幂等键。

1. 先验证身份和基础输入，再查该身份的已接受回执。同 session、同内容返回原成功响应，不重复记局数或写成绩；同 session、不同内容返回明确冲突。
2. 无回执时，验证原 session 归属、有效期、投放耗时及分数上限。
3. **凭证消费、成绩写入、局数累加、条件更新最佳成绩与接受回执必须在同一事务中完成。** 不能先消费凭证再执行成绩事务。
4. 并发请求只允许一个事务成为新接受者；其他事务读取回执返回。可使用唯一键和服务端本次处理标识约束后续写入，不能仅依靠事务外读到的 `used` 或旧最佳分数。
5. 写入失败整体回滚，原凭证仍可重试；已经成功的回执应在 TTL 判断之前返回，避免“服务端成功、回包丢失、稍后重试已过期”造成假失败。

响应继续兼容 `{ improved, best, rank }`，可增加 acceptedAt 等回执字段。重复请求返回首次接受时的结果；最新个人排名单独查询。游客绑定的既有成绩合并需要同步维护回执归属，不能让回执与成绩属于不同玩家。

新增迁移先在隔离 D1 验证，再部署兼容旧客户端的 Worker，最后更新前端。新 Worker 可为旧客户端的首次合法提交建立回执；升级前已消费却没有成绩关联的旧 session 不能凭猜测补造成功回执。

## 客户端待处理记录

- 按 API 环境和原 playerId 隔离，关联 T05 的稳定 roundId 与原 sessionId。保存不可变提交内容、重试状态和最近错误，不复制 token。
- 结算先持久化待处理结果，再移除未完成对局。刷新时若同 roundId 已进入结果队列，不得把旧棋盘当作未完成局恢复。这两个写入之间的中断必须有恢复判断。
- 若队列落盘失败，只能保留内存记录并提示风险；不能先删除唯一的可恢复数据再声称已暂存。已有在线凭证尚未返回时先限时等待，拿不到原凭证则明确无法补传，不补发新凭证冒充原局。
- 待处理记录采用独立条目，避免整张列表读改写造成新旧记录互相覆盖。确认成功后只删除对应条目；清理本机记录失败也不能把服务端成功改报为上传失败。
- 多标签页通过独立上传互斥协调。网络请求期间与存档写入权解耦，重开不覆盖旧请求；服务端幂等作为最后一道保护。
- 对积压数量设置可见上限（推荐每个环境最多 50 条待处理记录），达到上限不静默删除旧结果，明确提示先处理。成功记录无需无限积累在客户端。

## 重试与身份规则

推荐默认请求超时 8 秒。一次触发最多首次请求加 3 次自动重试，间隔约 2、5、15 秒；离线等待 online 事件再触发，手动重试另开有限尝试。限制重复事件和连续点击，避免多页产生请求风暴。

| 结果 | 处理 |
| --- | --- |
| 网络异常、超时、5xx | 保留并有限重试；超时视为结果未知 |
| 429 | 遵守 Retry-After；缺失时采用较长等待，不立即连发 |
| 401 | 暂停，要求原身份重新登录；不删除记录 |
| 当前身份与记录不同 | 不上传，显示等待原身份 |
| 确定的凭证无效／过期、内容冲突、规则拒绝 | 停止自动重试，保留可见原因 |
| 同 session 同内容已接受 | 返回原回执，清理该条待处理记录 |
| 本机写入失败 | 当前页保留，明确“未保存”；允许重试保存 |

游客绑定 LINUX DO 前如有未确认成绩，先引导完成补传或明确处理这些记录，不能绑定后静默更改待上传条目的 playerId。已上传成绩仍按现有规则合并。普通切账号不会替新账号认领旧成绩。

## 验收

- 请求未到服务端、写入中失败、写入成功但响应丢失、客户端成功后清理失败。
- 同内容串行／并发重试仅一条成绩、局数仅加一；不同内容重用凭证被拒绝。
- 高低分并发仍保留高分，同分保留原达成时间，T02 行为不回退。
- 刷新后补传、下一局进行时旧请求完成、两标签页同时补传。
- 账号切换、重新登录原身份、游客绑定前存在待处理成绩。
- 凭证在首次有效提交前过期；首次提交已成功，回包丢失后过期再重试。
- 429／401／规则拒绝不无限重试；损坏队列、存储失败、容量上限不静默丢数据。
- 旧客户端兼容、迁移前数据保留、隔离 D1 原子回滚与唯一键竞争。

## 已确认与实施

本轮已在浏览器检查桌面和 320px 竖屏；新局进行中处理旧成绩后，新局仍为 0 分且旧结算层未弹出；取消移除保留原记录。短屏结算区可滚动，主操作“再来一局”优先可见。上述为原型交互验证，不代表真实网络补传或服务端幂等已实现。

用户已确认结算上传状态与待处理入口，以及 **有限自动重试、原身份补传、本地局不补交、绑定游客身份前先处理未确认成绩**。已新增 D1 回执迁移，尚未部署线上环境。

实现中以小型结束记录原子替换未完成棋盘，再转入独立队列；中断后不会把该记录当作可续玩的棋盘。队列已满或写入失败时保留结束记录／当前页内存，并明确区分已保存与未保存；新局必要时降级为临时游玩，避免覆盖唯一结果。回执字段保持原三个字段兼容，通过“提交时”文案区分历史响应与实时排名。
