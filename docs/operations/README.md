# 效果评估与运行维护（T12）

这套工具读取已有 SQLite / D1 数据，生成聚合报告和清理候选。**不新增行为采集，不依赖付费分析服务，不迁移、不清理、不部署。** 源码为 `leaderboard/ops/report.mjs`、`leaderboard/ops/run.mjs`。

## 每轮迭代怎样记录

先指定同一数据源、北京时间统计区间和观察截止点。默认是当前观察点之前 7 天；自然日参数以北京时间 00:00 解释，区间左闭右开。输出 Markdown 供阅读，JSON 供下一轮比较，`.cleanup.sql` 仅供审查。快照推荐留在仓库外，避免发布不必要的运行信息。

本地已有数据库：

```sh
npm run ops:report -- --sqlite /absolute/path/database.sqlite --source local-test --from 2026-10-01 --to 2026-10-03 --out /absolute/path/reports/iteration-1
```

线上只读 D1（使用已经安装的 Wrangler，认证方式与本项目既有发布工具相同）：

```sh
npm run ops:report -- --remote --database clawd-merge --wrangler "$WRANGLER_BIN" --source production-m1 --out /absolute/path/reports/iteration-1
```

`WRANGLER_BIN` 应为本机已安装的 `wrangler/bin/wrangler.js` 的绝对路径。脚本不会安装工具或展示认证信息。远程查询仅允许 SELECT、WITH 和 EXPLAIN QUERY PLAN，没有写入命令。SQLite 以 readOnly 模式打开，并在同一读事务里采集；不存在的数据库不会自动创建。

下一轮增加 `--baseline /absolute/path/reports/iteration-1.json`，改用新的输出前缀。基线须为同一 source、schemaVersion，且观察点早于本轮。默认拒绝覆盖输出。行数差表示净变化，不能替代数据库物理字节增长或真实新增量。只有短时间内的两份快照也不足以评估长期增长。

## 统计口径

| 指标 | 数据来源与限制 |
| --- | --- |
| 被接受的经典成绩 | `scores.created_at` 落在区间内的记录数，含 0 分；旧记录缺少完整回执，不能追溯证明历史去重 |
| 经典幂等回执 | `score_receipts.accepted_at` 区间记录数；只反映具备回执机制的记录，不能当作全部历史完成局数 |
| 每日正式开局 | `challenge_sessions.started_at` 区间内凭证数；同 requestId 重放不新增 |
| 每日接受成绩 | `challenge_scores.accepted_at` 区间内记录数，session 主键保证同局重放不新增 |
| 有成绩的账号 | 在两类接受记录里按当前 `player_id` 去重；不是全部参与人数，更不是自然人数 |
| 重复参与观察 | 区间至少两条接受记录、或至少两个北京时间日期有接受记录的账号数；不叫留存率 |
| 每日凭证接受比例 | 区间内签发的凭证，截至 asOf 已对应接受记录的比例；包含区间后、观察点前接受的旧凭证；未截止数量单独列出 |
| 全部参与/真实完成/上传成功率 | **未知**：无匿名、离线、练习局完成事件，也无客户端发送尝试/失败分母 |
| 留存率/分享转化 | **未知**：没有完整首次参与队列与分享打开事件；不新增采集来凑数据 |

日期按北京时间；报告总数包括零分，排行榜只显示正分，这是两个不同口径。不要把“区间每日接受数 / 区间签发数”直接相除，因为它们不属于同一开局 cohort。

经典旧凭证已由开局流程清理，`retainedStarts` 只是仍留存的凭证数。账号合并会修改旧记录的归属，重建游客也会创造新身份；跨快照账号指标可能变化，不能解释为新增/流失的真实人数。数据库或 SQL 故障应导致报告失败，不能生成一份全零报告。尚未迁移每日表时显示未知；表存在且无记录时才显示观测零。

## 查询与存储

报告列出每张业务表行数、候选数量、经典/每日前 20 名查询计划和每条查询的耗时。D1 额外保留 rows_read / rows_written 元数据；本地 SQLite 的这些平台指标为未知，JSON 可记录 page_count × page_size 的逻辑大小，不能等同包含 WAL 的全部磁盘占用。

当前索引 `idx_players_best`、`idx_challenge_rank` 与榜单排序匹配，T12 没有新增索引。对周期统计来说，聚合与 COUNT 仍可能扫描历史表；建议每轮迭代手动生成快照，不用高频轮询。数据量增长后，依据 rows_read、查询计划、耗时和 D1 平台存储指标判断是否需要时间索引或日汇总，避免为尚不存在的瓶颈增加写入成本。

报告耗时包含 Wrangler 启动和网络往返，**不是**线上榜单响应延迟基准。远程采样由多条只读查询完成，表存量不是跨查询的事务一致快照。实际平台字节与配额仍看 D1 运维指标，不凭行数推测剩余容量。

## 保留与清理策略

| 数据 | 策略 |
| --- | --- |
| OAuth state | 创建超过 10 分钟可清理；登录流程本身也会清理过期记录 |
| 一次性 login code | 创建超过 2 分钟可清理 |
| rate_limits | 窗口起点超过 24 小时才列为候选，覆盖当前最长 24 小时限流窗口 |
| 经典未使用 session | 超过 3 小时有效期，再保留 24 小时后列候选 |
| 经典已使用 session | 仅当对应不可变回执已存在且接受超过 24 小时才列候选；无回执的旧已用凭证保留 |
| scores / score_receipts | 保留历史与回执，避免重试丢失幂等证明 |
| 每日 definitions / sessions / allowances / scores / bests | 全部保留。凭证及 requestId 支持旧开局重放，次数账本支持合并，不按“过期”直接删除 |
| tokens / players | 不因低活跃自动删除，不干扰已有登录 |
| 浏览器 pending / identity / rejected / corrupt 等待处理记录 | 不由服务端运维工具读取或清除；保留现有重试与用户明确移除流程，不自动丢弃离线结果 |

生成的 `.cleanup.sql` 使用固定 cutoff 和每条最多 500 行的子查询。报告操作只计数并输出文本；执行清理属于另一项写库操作，需先确认目标、时钟、备份、候选与回执保护，再按小批执行并核对剩余数量。**本次没有执行线上清理。** 工具没有定时任务、Cron、自动 DELETE 入口，也不会清理账号或挑战账本。

SQLite 和真实 workerd/D1 都已验证：候选删除后，经典/每日原回执仍能重放，挑战次数不变。不要把 `.cleanup.sql` 当作迁移自动应用；未来改变认证 TTL 或限流窗口时同步调整清理口径和测试。
